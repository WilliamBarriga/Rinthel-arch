# pnpm monorepo with packages and independence from consumers

pnpm workspaces with no task orchestrator (a few packages do not justify one). Vitest as runner and tsup for the build. Packages in `packages/`: `canonico` (Zod schema, validation, View resolution), `tema` (catalog, Resolved style and Slots), `dsl` (text to Canonical form, Workspace merge), `layout` (ELK and Pin), `sesion` (shared pipeline), `render` (pure React: Nodes and Groups in HTML/CSS, Edges in SVG), `shell` (pan/zoom, collapse, worker) and `cli`. Dependency order: `canonico -> tema -> dsl -> layout -> sesion -> render -> shell / cli` (see the amendments). `canonico` comes first because layout, render and cli consume it without needing the parser. `shell` is split from `render` so that any consumer imports only the pure drawing.

## Independence

This repo does not depend on any consumer repo or on a Documented project, nor the other way around in code. `render` is a package usable in isolation; step-by-step reveal is done with the `visibility` prop. The Workspace of a Documented project is chosen by the CLI user (`--workspace <path>`); the derived output goes to `<workspace>/.diagrams/` and is not versioned. Integrating the system into another repo is that repo's work, outside this one.

## Amendment: `sesion` package

`sesion` is added between `layout` and `render`/`shell`/`cli`: order `canonico -> dsl -> layout -> sesion -> render -> shell / cli`. It imports only `canonico`, `dsl` and `layout`. It is a pure function over the Workspace file map (no filesystem port: reading disk and watching changes are `cli` adapters), so CLI, `dev` and `inspect` share a single compile, validate and layout pipeline. Interface: `diagnosticar()`, `construir()` and `geometria(vista)` (lazy and memoized per View). See the term Session in `CONTEXT.md`.

## Amendment: `tema` package

`tema` is added (ADR 0008): order `canonico -> tema -> dsl -> layout -> sesion -> render -> shell / cli`. It is pure (it is in the core list of the purity check) and imports only `canonico`. It owns the catalog of Primitives and Slots, the strict schema of the resolved Theme, the Resolved style (Metrics and paint) and the Slot placement shared by `layout` and `render`.

Why after `canonico` and not before: Theme validation emits `Issue` with the codes of `CODIGOS` and suggestions from `candidatosCercanos`, which live in `canonico`; putting it before would have forced duplicating the error type or moving `Issue` up to `tema`. Why before `dsl`: the Theme compiler (a module of its own in `dsl`) validates every Layer and every Slot against the catalog. Consequence: the Canonical form only knows the Theme envelope (`name`, `palette`); `canonico` no longer has a Theme schema or Metrics, and neither does `layout` (`metricasDe` and `atributosVisibles` belong to `tema`). `pnpm check:deps` covers the new package (chain, exports and purity).

## Amendment: `estudio` package

`estudio` is added, the browser code of the Dev UI: order `canonico -> tema -> dsl -> layout -> sesion -> render -> shell -> estudio -> cli`. Everything that lived in `cli/navegador/` (page, SSE client, History, move, layout worker, Theme component loader) moves here; `cli` is left with no browser code. The Workspace's Theme `.tsx` files are still compiled on the fly in `cli`: they are Workspace data, not UI code.

Why a package and not `cli` or `shell`: `shell` is the reusable viewer any consumer imports and must not drag along the editor or the chrome; `cli` is the disk and server adapter, and mixing it with a browser app would bloat it with dependencies only the page uses. It is outside `NUCLEO`: it uses the DOM, `fetch` and `EventSource`.

Bundle at build time: the `estudio` build produces the static assets in `dist/` (page JS, worker JS, CSS; the CSS step is pluggable). Since #184 the page is a split ES module: what is imported with `import()` (the editor with CodeMirror, the Finder, the help) goes into `trozos/` with a hash and is requested on use; `activosDelEstudio()` lists them on every call. The bench budget measures the initial load of that real page. `dev` no longer bundles the UI on startup: `estudio` exports a minimal Node entry with the paths of its assets and `cli` serves them under `/_estudio/` with `no-store`, read from disk on every request (esbuild in watch mode over `estudio` and a reload are enough to iterate on the UI).

Contract of the `dev` protocol (amendment #201): it has a single owner, `canonico` (`src/dev.ts`). There live the routes (`RUTAS_DE_DEV`), the SSE event names (`EVENTOS_DE_DEV`) and the `EventoDeDev` type, the schemas of what the Live workspace produces (state, Diff, File history, activity, files, code, `inspect` not found, errors) and of the requests, and `estadoHttpDeRechazo`. `estudio/protocolo` only re-exports them for the page; `cli` imports only types from it or takes them from `canonico`. The event sequence (on connect: state, File history and activity with previous entries; after each state, its File history and its Diff) is written once by the Live workspace of `sesion` (`conexion` and `escuchar`); the real server and `devEnMemoria` only serialize it. Moving the protocol to `sesion` was discarded: `sesion` must not enter the browser bundle.

Amendment (#184): the core of the Live workspace (current and last good Session, History, queue, versions, Diff with origin by hash, Activity log) and the `/api/*` routes (`atenderApiDeDev`) live in `sesion`, over the `PuertoDelWorkspaceVivo` port with injected clock and time, together with `puertoEnMemoria`. `cli` keeps the disk port, the watcher, the on-disk log and the HTTP/SSE server; `devEnMemoria` from `estudio/contrato` is the same Live workspace over `puertoEnMemoria` with a fake transport.

Amendment (#208): `estudio` declares a third subpath, `estudio/construir` (`construirEstudio({ salida, css? })`), the entry that assembles the app bundle; the package build and the bench use it. The root `scripts/` and `bench/` consume the packages like any client: by name or by what `exports` declares, never their `test/` or `scripts/` by path (verified by `check:deps`). Shared test helpers (e.g. the Chromium helper) live in `tests/ayudas/`.
